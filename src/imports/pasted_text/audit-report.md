## 1. The form submission issue is real, and I found the primary cause

Your frontend is **not inserting directly into `public.enquiries`**.

`StartProject.tsx` sends the form to:

`/functions/v1/make-server-078be9eb/enquiries`

But the deployed Edge Function currently contains only:

* CORS middleware
* logging
* `/health`

There is **no `/enquiries` POST route at all**.

So the frontend is calling an endpoint that the deployed function does not implement. The form code is therefore structurally wired to the wrong backend path.

This explains the failure much more strongly than the earlier hypothesis about the textarea.

There is also a second issue: the frontend's error handling explicitly interprets a `404` as:

> “Our enquiry service is still being deployed.”

That message is misleading now because the function is active, but the route itself is missing.

### Important

The function has `verify_jwt: true`, while the website is sending the public `anon` key as the Bearer token. That may also become a problem depending on how the deployed function validates the request. More importantly, **you don't actually need this Edge Function for a simple public enquiry insert** if your RLS policy is designed for it.

# 2. The exposed Supabase key is NOT automatically a security vulnerability

This file is public:

`utils/supabase/info.tsx`

and contains the project ID plus the **anon/public key**.

That looks scary, but the key is explicitly the public/anon credential, not a service-role secret.

Supabase's current security guidance says a publishable key/legacy anon key is intended to be exposed in frontend applications, provided RLS and least-privilege grants are correctly configured. **The service-role/secret key must never be exposed client-side.**

So:

**Public anon key:** acceptable
**Service role / secret key:** dangerous

I did **not** find the service-role key hardcoded in the GitHub source files I inspected.

However, the repository is public, so this still needs a broader secret scan before we declare the repository clean.

# 7. Database performance findings

Supabase currently reports:

### Foreign-key index missing

`blog_posts.category_id`

has a foreign key but no covering index.

That should eventually be indexed because category-based blog queries and parent-side deletes/updates can otherwise become inefficient.

### RLS policy optimization

Two `user_profiles` policies repeatedly evaluate `auth.uid()`:

* `Users can insert their own profile`
* `Users can update their own profile`

Supabase recommends wrapping the auth call like:

```sql
(select auth.uid())
```

for better query planning.

This is a performance optimization, not a current functional failure.

### Multiple permissive policies

There are four cases where the same authenticated operation is being evaluated through multiple permissive RLS policies.

For example, `enquiries` has:

* admin management policy
* public insert policy

Both apply to authenticated users.

This isn't inherently broken, but it makes the policy model more complex than necessary.

# 10. There are SEO risks worth cleaning up

Not because Google will "punish" the website automatically, but because the implementation has some technical hygiene issues.

### Sitemap and SPA routing

The site uses a React SPA with manual routing.

Your sitemap contains a lot of journal URLs, which is good **only if those URLs actually resolve correctly and contain the corresponding content**.

Because the app is client-side rendered, Google can render it, but this is not equivalent to having server-rendered HTML for every URL.

That's an architectural SEO consideration.

### Metadata duplication

You currently have metadata in:

`index.html`

and additional metadata dynamically injected from `App.tsx`.

That can create multiple competing definitions or unnecessary DOM churn.

### Google Analytics + GTM

You have:

* GTM in `index.html`
* GA configured in `.figma/make/site.json`
* GA injection logic inside `vite.config.ts`
* `dataLayer.push()` in `App.tsx`

That is a **very important duplication**.

It doesn't necessarily break tracking, but it can lead to:

* duplicate page views
* duplicate events
* inflated analytics
* harder debugging

This is one of the areas I'd clean up carefully.
